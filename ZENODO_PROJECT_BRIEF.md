## 1. Краткое описание (elevator pitch)

**Legion** — дополнительный слой кибербезопасности для обычного пользователя браузера.  
Цель — снижать риск фишинга и скама на **страницах-однодневках**, которые ещё не попали в корпоративные чёрные списки антивирусов и Safe Browsing.

Продукт **не заменяет** антивирус и не претендует на полный контроль угроз.  
Он срабатывает **только после анализа** и при наличии оснований для тревоги (или мягкой осторожности), а не из‑за одного факта «на сайте есть форма входа».

---

## 2. Проблема, которую закрывает проект

### 2.1. Практическая проблема
Современные защитные системы часто **реактивны**: сверяют URL с уже известными базами.  
Мошеннические сайты-однодневки успевают собирать пароли, карты и коды подтверждения в первые часы жизни, пока записи в реестрах ещё нет.

Дополнительный риск — **социальная инженерия**: срочность («осталось 3 минуты»), угроза блокировки, имитация Госуслуг/банков/Steam, просьба «пароля от другого сервиса».

### 2.2. Темы / предметные области
- кибербезопасность конечного пользователя (browser security);
- антифишинг и борьба со страницами-однодневками (zero-day phishing pages);
- социальная инженерия и манипулятивные тексты на веб-страницах;
- эвристический и гибридный анализ риска (локальные правила + внешние базы + опционально LLM);
- приватность при клиентской защите (минимизация данных, уходящих наружу);
- UX предупреждений: блокирующий (красный) и осторожный (жёлтый) режимы.

### 2.3. Что продукт сознательно НЕ делает
- не является антивирусом / EDR / полной заменой Safe Browsing;
- не сканирует служебные страницы браузера и Chrome Web Store (ограничение платформы);
- не требует аккаунта пользователя и облачной авторизации;
- не отправляет полную историю кликов на внешний сервер.

## 3. Идея и подход

### 3.1. Базовая идея
Сместить акцент с «только имя домена в чёрном списке» на **протокол ступеней**:

1. доверенные сайты пропускать мгновенно;  
2. уже известные угрозы отсекать по базам;  
3. неизвестный сайт анализировать **глубоко только если** на странице есть риск ввода конфиденциальных данных;  
4. предупреждать пользователя **после подтверждения риска**, а не при любом логине.

### 3.2. Ключевые продуктовые принципы
- **Скорость и приватность** достигаются архитектурой (ступени + кэш), а не отказом от надёжных слоёв.  
- **Форма ≠ угроза**: обычный вход на неизвестном сайте может дать жёлтую осторожность, но не обязательный красный оверлей.  
- **Локальный fallback**: без backend расширение продолжает работать на whitelist/blacklist и локальных эвристиках.  
- **Минимум ложных блокировок**: brand spoof требует подтверждения вторым сигналом; алиасы брендов ищутся по границам слов.

## 4. Протокол принятия решения

```
whitelist (домен и поддомены) / exactDomains
    → safe

кэш вердикта по отпечатку содержимого
    → повторно не считаем

локальный blacklist ИЛИ Google Safe Browsing hit
    → danger (красный оверлей)

нет релевантных форм / ПДн
    → safe («угроз не обнаружено»)

локальные эвристики текста + brand spoof + lookalike
    → danger при высоком риске / spoof с подтверждением / critical + cross-origin
    → caution (жёлтый) при tier A или B
    → иначе safe

опционально: «серый» риск + LLM (OpenAI-compatible, напр. DeepSeek)
    → уточнение вердикта
```

### 4.1. Режимы для пользователя

| Режим | Индикатор | Поведение |
|-------|-----------|-----------|
| Проверка | серый `…` | идёт анализ |
| Безопасно | зелёный `✓` | whitelist или нет оснований для тревоги |
| Осторожность | жёлтый `?` | экран не блокируется; пользователь видит причины |
| Угроза | красный `!` | полноэкранное предупреждение; «Уйти» / «Всё равно продолжить» |
| Особый | серый `·` | продолжил на свой риск / страница недоступна сканеру |

### 4.2. Жёлтый режим (осторожность)
- **Tier A:** неизвестный сайт + критичные поля (пароль / карта / документы / OTP).  
- **Tier B:** мягкие ПДн (email / телефон / имя) **и** доп.сигнал (lookalike, brand на чужом домене, cross-origin form, HTTP).

Критичность считается по **реальным полям ввода**, а не по упоминанию слова «пароль» в справке.

## 5. Технический стек

| Слой | Решение |
|------|---------|
| Клиент | Chrome / Edge / Brave, **Manifest V3** |
| Content script | детект DOM/форм/модалок/Shadow DOM, сбор сниппетов |
| Service worker | оркестрация протокола, бейджи, состояние вкладок |
| UI | popup + options (технический интерфейс; финальный дизайн подключается отдельно) |
| Backend | **Python 3 + FastAPI + Uvicorn** (`127.0.0.1:8787`) |
| Этап 1 | локальный `whitelist.json` (+ пользовательский список в настройках) |
| Этап 2 | локальный `blacklist.json` + **Google Safe Browsing Lookup API v4** |
| Этап 3a | локальные regex-эвристики, brand spoof, lookalike (Дамерау—Левенштейн) |
| Этап 3b | LLM через OpenAI-compatible API (опционально, только на сером риске) |
| Данные брендов | `brands.json` (Госуслуги, банки, VK, Steam и др.) |
| Кэш | вердикты по содержимому; health/SB кэшируются на стороне клиента |
| Статистика | модуль backend (`/v1/stats`), отображение в popup; CLI `stats.ps1` для разработки |
| Секреты | только в `backend/.env`, не в расширении |

## 6. Способ реализации (архитектура)

### 6.1. Клиент (расширение)
1. Content script наблюдает страницу (мутации, фокус, периодический скан).  
2. Собирает hostname, признаки форм, типы полей, cross-origin action, текстовые сниппеты.  
3. Отправляет payload в service worker.  
4. Service worker запускает `runProtocol` и выставляет статус вкладки / бейдж.  
5. При `danger` показывает блокирующий overlay (`HTMLDialogElement.showModal`).  
6. Вердикты кэшируются; после Reload расширение само поднимает сканер на открытых вкладках.

### 6.2. Backend (опциональное усиление)
- `GET /health` — статус сервиса, SB/LLM, сводка stats;  
- `POST /v1/threat-check` — Safe Browsing (наружу уходит origin+path **без query**);  
- `POST /v1/analyze` — эвристики + опционально LLM;  
- `GET/POST /v1/stats*` — учёт вердиктов (fire-and-forget с клиента, на защиту не влияет).

CORS ограничен origin’ами вида `chrome-extension://…`.

### 6.3. Приватность при реализации
- на сторонние API не уходит полный URL с токенами в query;  
- LLM/анализ получают укороченные сниппеты, а не полный DOM;  
- без backend продукт остаётся работоспособным локально;  
- пользовательская авторизация **не используется** (избыточна для локальной модели).

## 9. Предлагаемый abstract (черновик на 120–180 слов)

Можно вставить в Zenodo почти как есть и доработать под стиль журнала/конференции:

> Legion is a browser extension (Chrome Manifest V3) with an optional local FastAPI backend that provides an additional protection layer against phishing and scam one-day websites. Unlike purely reactive blocklist-based approaches, Legion applies a staged protocol: trusted domains are passed immediately; known threats are checked via a local blacklist and Google Safe Browsing; unknown sites are analyzed only when sensitive input forms are present. Local text heuristics, brand-spoof and lookalike detection produce a risk score; a blocking red overlay is shown only after confirmed risk, while a yellow caution mode warns without interrupting browsing. The system is designed for privacy (minimal outbound data, no click-history telemetry, no user accounts) and continues to operate with local heuristics when the backend is offline. The project is intended as complementary protection for end users, not as a replacement for antivirus software.
